# Inverted pendulum on a cart — план проекта

## 1. Цель

Разработать контроллер для маятника на тележке, который:

1. сначала проверяется в воспроизводимой компьютерной симуляции;
2. затем переносится на реальный макет через тот же интерфейс датчиков и исполнительного механизма;
3. способен безопасно работать при неизвестных или неточно известных параметрах тележки, маятника, трения и привода;
4. постепенно уточняет параметры по измерениям, не передавая управление неконтролируемому адаптивному алгоритму.

Главный принцип: **сначала безопасный базовый контур и сбор данных, затем идентификация, затем адаптация**. Без измеримых сигналов и ограничений по безопасности адаптация не может гарантировать устойчивость.

---

## 2. Что именно неизвестно и как это решаем

### Потенциально неизвестные параметры

- масса тележки `M`;
- масса маятника `m`;
- расстояние от оси до центра масс `l`;
- момент инерции маятника `I`;
- сухое и вязкое трение тележки и оси;
- коэффициент тяги двигателя и редуктора;
- задержка привода и ограничения по скорости/току;
- ноль энкодера и ноль угла маятника.

### Разделение на типы параметров

Не все параметры нужно восстанавливать физически. Для первого рабочего контроллера достаточно оценить эффективную модель:

- коэффициенты связи силы/ШИМ с ускорением тележки;
- коэффициенты влияния угла и угловой скорости на ускорение;
- задержку и насыщение привода;
- параметры трения в рабочем диапазоне.

Физические `M`, `m`, `l`, `I` можно использовать для интерпретации и симуляции, но контроллер не должен зависеть от их точного ручного измерения.

### Предлагаемый подход к адаптации

1. **Калибровка на месте:** ноль датчиков, направление знаков, диапазоны, механические пределы.
2. **Пассивный сбор данных:** небольшие безопасные тестовые воздействия на опущенном маятнике или при зафиксированном маятнике.
3. **Онлайн-оценка:** рекурсивный метод наименьших квадратов (RLS) с нормировкой, забыванием и проверками качества данных.
4. **Безопасное применение оценки:** контроллер использует параметры только после проверки ошибок, диапазонов и достаточной возбуждённости системы.
5. **Ограниченная адаптация:** скорости изменения коэффициентов и диапазон gain scheduling ограничены; при сомнении происходит возврат к консервативным настройкам.

В первой версии не следует начинать с полностью адаптивного закона управления. Рабочая последовательность: **номинальный LQR/PD в симуляции → робастный базовый контроллер → идентификация → осторожная адаптация**.

## 3. Архитектура проекта

Код следует разделить на слои, чтобы симулятор и реальный макет использовали один и тот же контроллер:

```text
sensors/actuator interface
          ↓
  timestamp + validation
          ↓
 state estimator (position, velocity, angle, angular velocity)
          ↓
 identification / parameter estimator
          ↓
 controller (swing-up / balance)
          ↓
 safety supervisor + saturation
          ↓
 actuator command
```

Предлагаемая структура репозитория:

```text
src/cart_pendulum/
  model.py             # нелинейная модель и параметры
  simulation.py        # дискретный симулятор и возмущения
  estimation.py        # фильтры и оценка состояния
  identification.py    # RLS/оценка параметров
  control.py           # swing-up, балансировка, переключение режимов
  safety.py            # лимиты, watchdog, аварийное отключение
  interfaces.py        # общие интерфейсы датчиков и привода
configs/               # конфигурации стенда, без секретов
examples/              # запускаемые эксперименты и графики
tests/                 # unit-, property- и integration-тесты
docs/
```

На этапе симуляции интерфейс привода должен принимать нормированную команду, например `u ∈ [-1, 1]`. Преобразование в PWM/ток/скорость нужно оставить в аппаратном адаптере, чтобы модель управления не зависела от конкретного драйвера.

## 4. План работ по этапам

### Этап 0 — требования и контракты

**Задачи**

- [ ] Зафиксировать координаты и знаки: `x` — положение тележки, `theta = 0` — вертикально вверх или вниз, положительное направление движения.
- [ ] Зафиксировать единицы: метры, секунды, радианы, Н·м или нормированная команда.
- [ ] Описать доступные датчики: энкодер тележки, энкодер/IMU маятника, частота и задержка измерений.
- [ ] Описать привод: тип двигателя, редуктор, способ управления, максимальная команда, ток и скорость.
- [ ] Зафиксировать длину рельса и механические пределы.
- [ ] Определить целевые частоты цикла управления и логирования.
- [ ] Согласовать критерии успеха и сценарии аварийной остановки.

**Результат:** `docs/hardware_spec.md` с заполненными значениями или явными `TBD`.

**Критерий готовности:** любой разработчик может однозначно понять, что измеряется, в каких единицах и что считается опасным состоянием.

## 5. Безопасность как отдельный модуль

Контур безопасности не должен быть частью только регулятора. Минимально необходимы:

- аппаратная аварийная остановка;
- программный watchdog цикла;
- проверка диапазонов `x`, `theta`, скоростей и команды;
- ограничение по положению тележки с зоной торможения;
- отключение при пропаже или рассинхронизации датчиков;
- отключение при слишком большой угловой скорости или выходе маятника из допустимой зоны;
- ограничение скорости изменения команды;
- явный `FAULT` с ручным сбросом;
- логирование причины отключения;
- механический страховочный трос/ограничитель на этапе испытаний.

Проверки безопасности должны выполняться и в симуляции. Любой тест с реальным макетом должен начинаться с малой команды и иметь заранее заданное условие abort.

## 6. Метрики эксперимента

Для сравнения алгоритмов нужно сохранять одинаковый набор метрик:

- время удержания около верхнего положения;
- максимальная и RMS ошибка `theta`;
- максимальная ошибка положения `x`;
- время восстановления после возмущения;
- доля времени в насыщении привода;
- максимальный ток/команда и скорость её изменения;
- ошибка прогноза идентификатора;
- число срабатываний safety/fault;
- задержка и частота цикла управления.

Минимальная запись эксперимента: конфигурация, версия кода, seed/идентификатор запуска, сырые датчики, оценка состояния, команда, оценённые параметры и причина завершения.

## 7. Первый инкремент

Чтобы не пытаться сделать весь проект сразу, первый рабочий инкремент включал только:

1. [x] шаблон конфигурации с единицами и знаками;
2. [x] интерфейсы `Measurement`, `State`, `ActuatorCommand`;
3. [x] нелинейную симуляцию с фиксированным шагом;
4. [x] тесты на размерность, знаки, wrap-around и отсутствие NaN;
5. [x] простой запуск, сохраняющий CSV одного эксперимента;
6. [x] базовый safety supervisor, работающий уже в симуляции.

**Не включены в первый инкремент:** реальный драйвер двигателя, EKF, swing-up, онлайн-адаптация и автоматическая настройка gain. Эти части зависят от подтверждённой модели интерфейсов и измерений.

Для запуска:

```bash
PYTHONPATH=src python -m unittest discover -s tests -v
PYTHONPATH=src python examples/run_simulation.py
```

## 9. Definition of Done для проекта

Проект можно считать завершённым, когда:

- контроллер проходит автоматические тесты и воспроизводимые симуляционные сценарии;
- одна и та же логика контроллера запускается с симулятором и с аппаратным интерфейсом;
- неизвестные параметры оцениваются по логам и/или онлайн с ограничениями;
- safety supervisor останавливает систему при каждом заданном опасном сценарии;
- есть журнал и replay каждого аппаратного эксперимента;
- на реальном макете подтверждены балансировка, восстановление после малых возмущений и корректный fault/fallback;
- настройки, ограничения и известные допущения описаны в репозитории.
